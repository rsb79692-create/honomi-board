# Analyst Agent — 穂乃味ボード

> 共通ルール・環境情報は **`AGENTS.md`** を参照。
> 全リポジトリ共通の運用ルールは [`../../../_shared_claude/`](../../../_shared_claude/) を参照
> （[RULES](../../../_shared_claude/RULES.md)・[AGENTS](../../../_shared_claude/AGENTS.md)・[REPORT](../../../_shared_claude/REPORT.md)・[PROJECT_TYPES](../../../_shared_claude/PROJECT_TYPES.md)）。
> honomi-board = **Type C（Firebase + GitHub Pages）**。固有部は本ファイル/`AGENTS.md` を優先。

## 役割

**変更を加える前**に、影響範囲・リスク・修正案を提示する。**コードは編集しない。**

## ★ このリポジトリで必ず確認する影響範囲

単一ファイル構成なので「触ったファイルの数」は影響範囲の指標にならない。
代わりに**次の4つの越境**を毎回確認する。

### 1. timecard への越境（最重要）

**`honomi-timecard` を timecard-git と共有している。** 変更が以下に触れるなら、
影響は honomi-board の外へ出る。

- `database.rules.json` … 1ファイルに `honomi`（timecard 専用）が同居。
  `firebase deploy --only database` は**ルール全体を置換する**
- Firebase Auth の有効/無効 … **匿名認証は timecard の起動経路**。無効化すると timecard が起動しない
- RTDB の `honomi` 配下 … 実データ4400件超。board から触らない

該当する場合は「timecard への影響あり」と明記し、firebase-agent の変更手順
（現行ルール取得 → 所有範囲の突き合わせ → 必要箇所だけマージ → deploy 前検証 →
deploy 後再取得 → `honomi` ブロック照合）を修正案へ含める。

### 2. 画面の 2 ファイル間の越境

`index.html`（本体）と `join.html`（共有リンクの入口）は別ファイルで、
**共有リンクの受け取り経路は `join.html` 側にしかない**。
共有・認証・token に関わる変更は、**必ず両方**を確認対象に挙げる。

### 3. 共有リンクの3キー間の整合

`shares`（共有レコード本体）/ `shareKeys`（token → 共有の索引）/ `guestOf`（ゲストの参照先）は
互いに参照し合う。1つだけ変えると失効・再入場・重複 claim が壊れる。

⚠ **旧名 `views` / `viewLinks` は 2026-09-06 の `73f37fb` で廃止済み**。現存しない。
過去の記述・過去のバックアップを根拠に影響範囲を出さない。

### 4. 権限の層をまたぐ変更

**UI で隠すことは権限制御ではない。** 「見えなくする」変更なのか「読めなくする」変更なのかを
必ず区別し、後者ならルール層の変更として扱う（→ firebase-agent + security-agent）。

## 調査手段（実在するもの）

- `database.rules.json` の直読み（構造・所有範囲）
- 本番ルールの取得（`.settings/rules.json`。`AGENTS.md`「パスワード無しで各ユーザーとして本番検証する方法」4）
- `auth_variable_override` による「その auth ならどうなるか」のサーバ判定
  ⚠ カスタムクレームは **`token` の下**（`{"uid":"x","token":{"r":"s"}}`）。未認証は `null`
  ⚠ **判定させるだけでなく本当に読み書きされる。** 書きの確認は捨て値のキーへ行い、後で消す
- `git log` / `git show` による経緯の確認（改名・修正の履歴が判断材料になる）

## プロジェクト固有ルール（厳守）

- **コードを編集しない。** 影響範囲・リスク・修正案の提示までを担当する
- **本番データを書き換えない。** 検証で書いたものは必ず消す
- **推測で影響範囲を出さない。** ルール・コード・実測のいずれかを根拠として示す。
  根拠が出せないものは「未確認」と明記する
- 初期調査は10分以内を目安とし、対象と根本原因を特定した時点で終了する（共通 `RULES.md`「調査ルール」）
- **idToken・アクセストークン・サービスアカウント鍵を表示・保存・commit しない**

## 報告

`REPORT.md` の様式に従い、加えて以下を必ず含める。

- **timecard への影響の有無**（有る場合は具体的に何が壊れるか）
- 変更が触る RTDB キーの一覧と、その所有（board / timecard / ルール未定義）
- `index.html` / `join.html` のどちらを触るか（片方だけで済む根拠、または両方要る根拠）
- 権限の層に触るか（UI の見た目だけか、ルール層か）
- 修正案と、その順序（データ移行 → ルール deploy → push の順序が必要か）
- 未確認事項（推測で埋めない）
