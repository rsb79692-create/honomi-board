### timecard（`honomi`）の認可（2026-09-06 に作り替えた）

⚠⚠ **これは timecard-git の持ち物だが、ルールは同じファイルに同居している。**
片方だけを直すことはできない。変えるときは必ず両リポジトリを同時に扱うこと。

⚠ **この節は 2026-09-06 時点の記述で、その後の timecard のマルチテナント化を反映していない。**
2026-09-26 時点の本番ルールでは、`honomi` の条件に `auth.token.c == null || auth.token.c === 'honomi'`
（他社テナントのトークンを締め出す）が加わった。
各社のデータは `tenants/$cid`（`c` クレームと `tenantReg` で判定。匿名の起動面は無い）に分かれ、
そちらには役割 `k`（打刻端末）がある（`honomi` 側には `k` は無い）。
**`honomi` / `tenants` の認可の正は `database.rules.json` そのものと timecard-git の `AGENTS.md`**とし、
下の表で判断しないこと。下記「残っている穴」（匿名で `tc5_pins` を読める）は `honomi` については今も当てはまる。

**それまでの状態（穴）**

`honomi` の `.read` / `.write` はどちらも `auth != null && guestOf に居ない` だけだった。
匿名サインアップは公開 apiKey で誰でもできるので、これは実質「誰でも勤怠データを
読み書きできる」と同じだった。4,500 件の打刻・26 人の氏名・**平文の PIN 30 件**が対象。

**いまの条件**

| 領域 | 読み | 書き |
|---|---|---|
| `tc5_staff` / `tc_master_depts` / `master/locations` | 起動面 | 役割つき（`s`/`a`）だけ |
| `tc5_pins` / `tc5_records` | 起動面 | 起動面。ただし**読み取り専用の役割は除外**し、**丸ごと消す操作は拒否** |
| `viewerTokens/$t` `demoTokens/$t` `staffDemoTokens/$t` | 起動面（**1件ずつだけ**。親に `.read` が無いので一覧不可） | `viewerTokens` は `a`/`d` |
| `demoIssuedViewerTokens` | 役割つき | `a`/`d` |
| **それ以外すべて** | **役割つき**（`honomi` 直下の `.read`） | **`s`/`a` だけ**（`honomi` 直下の `.write`） |

- **起動面** … `auth != null && guestOf に居ない`。打刻端末（匿名）はここ。
- **役割つき** … 上に加えて `auth.token.r != null` かつ `sx`（期限）が切れていないこと。

`r` は timecard の `/api/auth/{staff,admin,share}` がカスタムトークンへ入れるクレーム。
`s`=スタッフ / `a`=管理者 / `v`=労務士 / `d`=デモ / `x`=スタッフ用サンドボックス。
**匿名アカウントを自分で作っただけでは `r` が付かない**ので、承認・有給・賄い・資料・
`config`（管理者トークン）・各種トークンの一覧には一切届かない。

⚠ **書けるのは `s` と `a` だけ。** `v`（労務士）と `x`（サンドボックス）は読むだけ、
`d`（デモ）は閲覧リンクの発行枝だけ書ける。以前は「UI で書けないようにしてある」だけで、
REST から `PUT /honomi/tc5_records.json` に `null` を送れば**全件消せた**。
⚠ **`tc5_pins` / `tc5_records` は「丸ごと消す」だけ拒否する**（`.write` に `newData.exists()`）。
1件の追加・修正・削除は今までどおり通る。打刻を守りつつ、匿名1つで全消しされるのを止めるため。
⚠ **共有リンクの役割には期限（`sx`）が効く。** 以前は閲覧用URLを止めても、
相手が持っているリフレッシュトークンで役割トークンを更新し続けられた。


→ ⚠⚠ **残っている穴（いちばん大きい。次に直すならここ）**
`tc5_pins` には **PIN の平文（`plain`）** が入っており、起動面なので**匿名で読める**。
つまり第三者が
① 公開 apiKey で匿名アカウントを作る → ② `tc5_pins` を読んで氏名と PIN を得る →
③ `/api/auth/staff` を1回叩いて `r:"s"` を得る、で**役割つきの領域まで入れてしまう**。
`plain` を消しても、4桁 PIN の非ソルト SHA-256 は1万通りの総当たりで戻せるので同じことになる。
塞ぐには次の3つが要る。
1. `tc5_pins` の読みを役割つきに戻す。そのために「PIN を登録済みか」の真偽だけを持つ
   別ノード（照合材料を含まない）を起動面へ置く
2. `sOk` のローカル照合をやめ、`/api/auth/staff` の応答で判定する（サーバ照合は既にある）
   ⚠ **これは打刻に Vercel への依存を持ち込む。** いま Vercel が落ちても打刻はできるが、
   そうでなくなる。ここが最大の判断どころ。
   （なお `tc5_pins` は localStorage へ保存していないので、**オフラインでの PIN ログインは今もできない**。
    オフライン打刻は「ログイン済みのまま圏外になった場合」の話で、そこは変わらない）
3. 既存の PIN を全部入れ替える（漏えい済みとして扱う）
**この作業は今回やっていない。** 打刻の認証経路そのものを変えるうえ、
スタッフ PIN と管理者 PIN が手元に無く「正規利用者が従来どおり操作できる」ことを実測できないため。

⚠ **役割つきの領域を読む前には、必ず昇格を待つこと。**
timecard の `elevateStaffSession` / `elevateShareSession` は画面遷移を待たせないため
**裏で走らせている**。待たずに読むと匿名トークンのまま 401 になる。
timecard 側に `afterElevation()` を用意したので、それを使う。

⚠ **`s`（一般スタッフ）の役割でも `/honomi` 全体を読める。**
`.read` は `r` の値を見ていないので、PIN を持つスタッフは `config`・`documents`・
`viewerTokens` の一覧まで読める。管理者への昇格は `/authz` 側（`pin-set.js` の失効検証）で
止まっているので即座の権限昇格にはならないが、内部者に対しては広い。
ノードごとに `a` / `s` を分けるのは次の作業。

⚠ **`tc5_staff` の匿名読み取りには氏名だけでなく社員番号・所属・雇用区分も入っている。**
起動時のスタッフ選択に本当に要るのは表示名と読みだけ。分けるなら別ノードへ切り出す。

⚠ **GitHub Actions は匿名サインアップをやめた。**
`fcm-check.js`（30分ごと）と `notify-check.js`（手動）は、役割つきの領域を読むので
**サービスアカウントの OAuth2 アクセストークン**（`Authorization: Bearer`）で入る。
`morning-check.js` は `tc5_records` と `master/locations` しか読まないため**無変更**。
⚠⚠ **`FIREBASE_API_KEY` の GitHub Secret は消さないこと。** morning-check だけが今も使う。
⚠ サービスアカウントのアクセストークンは**ルールを全部迂回する**。同じ RTDB に同居している
ボード側（`rooms` / `shares` / `members` / `field`）まで届くので、この鍵を置く場所は増やさない。
